# Car360 לאנדרואיד: תכנית המרה

> המסמך מבוסס על מעבר על כל הקוד בריפו (כ-11,000 שורות: 13 מסכים, מערכת העיצוב, שכבת הנתונים, ההתראות, ה-Cloud Functions וה-CI).
> הוא מתאר **מה** נבנה, **איך**, **באיזה סדר**, ומה צריך ממך בדרך.

---

## 0. בקצרה

1. **טכנולוגיה:** אפליקציית **React Native (Expo)** נייטיב אמיתית, לא אתר עטוף. הלוגיקה (טיפוסים, תזכורות, דוח רכב, פורמטים, חיפוש) עוברת כמו שהיא. שכבת ה-UI נכתבת מחדש מרכיבים נייטיב.
2. **הריפו:** האפליקציה יושבת בתיקייה `mobile/` באותו ריפו. קוד משותף עובר ל-`shared/`. **אתר ה-web ממשיך לעבוד** (קישורי הדרכון הציבורי `/p/:token` חייבים דפדפן, ובני משפחה עם אייפון ממשיכים להשתמש בו).
3. **עדכונים:** GitHub Actions בונה APK חתום בכל push ל-`main` ומפרסם אותו ב-GitHub Releases. בהגדרות יש כפתור "בדיקת עדכונים": הורדה עם פס התקדמות בתוך האפליקציה והתקנה בלחיצה. **ההתקנה הידנית היחידה היא של ה-APK הראשון.**
4. **התראות:** שתי שכבות. **תזמון מקומי במכשיר** (עובד גם בלי שרת ובלי אינטרנט), ומעליו **FCM נייטיב** מהשרת. בנוסף מסך אבחון שעונה על "למה לא קיבלתי התראה?".
5. **עיצוב:** שפת עיצוב אחת, אחידה, מבוססת Material 3 ומותאמת לזהות של Car360 (Heebo, שני הגוונים של הפלטה, פינות מעוגלות). כל רכיב עובר דרך ספריית רכיבים אחת. כלל lint חוסם שימוש ברכיבי ברירת מחדל, ומסך "גלריית עיצוב" מציג כל רכיב בכל מצב.
6. **הגנות:** דיאלוג לפני כל מחיקה. חסימת יציאה עם שינויים שלא נשמרו, כולל **מחוות "חזרה" של אנדרואיד**. טיוטות נשמרות אוטומטית למקרה שהמערכת הורגת את האפליקציה (קורה כשפותחים מצלמה).
7. **סדר עבודה:** 8 אבני דרך (M0–M7). בסוף כל אחת יוצא APK שמגיע אליך דרך כפתור העדכון.

## 2. ההחלטה הטכנולוגית

### ההמלצה: React Native עם Expo (New Architecture, Hermes)

- **חלקות:** אנימציות ומחוות רצות ב-UI thread נייטיב (Reanimated + Gesture Handler), לא בתוך WebView. גלילה, גיליונות, החלקה בין רכבים וזום על תמונות מרגישים כמו כל אפליקציית אנדרואיד טובה.
- **רכיבים נייטיב אמיתיים:** שדות קלט עם טיפול נכון במקלדת, מעבר "הבא" בין שדות, bottom sheets נייטיב, ViewPager, רשימות ממוחזרות, ו-ripple של אנדרואיד.
- **Firebase נייטיב** (`@react-native-firebase`): Firestore עם offline persistence שעובד, listeners בזמן אמת (שינוי שבן משפחה עשה מופיע מיד), ו-FCM נייטיב אמין.
- **שימוש חוזר בקוד:** TypeScript נשאר TypeScript. כל הלוגיקה ב-`shared/` משותפת ל-web ולאנדרואיד.
- **בונוס:** אותו קוד יכול לשמש בעתיד גם לאפליקציית iOS.

**למה לא Capacitor:** היא עוטפת את אותו אתר ב-WebView, בדיוק תחושת "אתר מותאם" שרוצים לצאת ממנה, ו-`backdrop-filter` (הזכוכית) כבד מאוד ב-WebView של אנדרואיד.
**למה לא Kotlin/Compose:** הכי נייטיב, אבל אפס שימוש חוזר בקוד, ושני בסיסי קוד שונים לתחזק (web ואנדרואיד).

## 3. שפת העיצוב

### עקרונות

1. **שפה אחת.** בלי "סקינים". סקין הזכוכית נשען על טשטוש רקע, שבאנדרואיד עולה בפריימים וגם יוצר שתי שפות עיצוב שונות. נשארים: 5 פלטות, צבע דגש אישי, בהיר/כהה/לפי המערכת. אופציונלי: פלטת "צבעי המערכת" (Material You) באנדרואיד 12 ומעלה.
2. **Material 3 כשלד, Car360 כנשמה:** מבנה, מידות, מחוות והתנהגות לפי Material 3, כדי שהאפליקציה תרגיש בבית באנדרואיד. הזהות נשארת: Heebo במשקלים כבדים לכותרות, פינות מעוגלות נדיבות, ושני גוונים לכל פלטה (עמוק לפעולות ראשיות, חי ל-FAB, לבחירה ולמצב פעיל).
3. **אין רכיב ברירת מחדל.** מסך לא מייבא `TextInput`, `Switch`, `Pressable`, `Modal` או `Alert` ישירות מ-React Native, רק מ-`src/ui`. נאכף ב-lint (פרק 5).
4. **כל רכיב מגיע עם כל המצבים:** רגיל, לחוץ (ripple), פוקוס, מושבת, טוען, שגיאה, ריק. כל רכיב מוצג בגלריית העיצוב.
5. **מגע:** יעד לחיצה של 48dp לפחות. ripple בכל דבר לחיץ. משוב הפטי (haptic) לפי סוג הפעולה: בחירה, החלפה, הצלחה, שגיאה.
6. **תנועה עם תכלית:** 150–350ms, easing של M3. בלי המתנות מלאכותיות: טוען "בונה את העיצוב מחדש…" של 1.35 שניות יוצא, והחלפת פלטה הופכת ל-crossfade מיידי. מכבדים את הגדרת "הסרת אנימציות" של המערכת.

## 5. "אין אלמנט ברירת מחדל": אכיפה ורשימת בדיקה

באתר הנוכחי לא מצאתי רכיב שנשאר לא מעוצב: אין `alert`/`confirm` של דפדפן ואין `<select>` נייטיב. **הסיכון גדל דווקא במעבר לנייטיב**, כי שם יש הרבה ברירות מחדל שקטות. הרשימה המלאה, וכל פריט מקבל עיצוב:

| ברירת מחדל באנדרואיד | מה עושים |
| --- | --- |
| קו תחתון של `TextInput` (`underlineColorAndroid`) | שקוף, כי המסגרת שלנו |
| צבע הסמן, הבחירה וידיות הבחירה | `cursorColor`, `selectionColor`, `selectionHandleColor` מהפלטה |
| `Alert.alert` (דיאלוג מערכת אפור) | **אסור**. רק `Dialog` שלנו |
| `ToastAndroid` | **אסור**. רק `Snackbar` |
| `ActivityIndicator` בצבע ברירת מחדל | `Spinner` שלנו |
| ספינר של pull-to-refresh | `colors` + `progressBackgroundColor` מהטוקנים |
| ripple ברירת מחדל (אפור) | `android_ripple` בצבע ה-`onSurface` של הפלטה, מוגבל לצורת הרכיב |
| סרגל סטטוס וסרגל ניווט של המערכת | edge-to-edge, שקופים, אייקונים בהירים/כהים לפי המצב |
| Splash screen | רקע הקנבס + לוגו Car360, ומעבר רך לאפליקציה |
| אייקון אפליקציה | adaptive icon + **אייקון מונוכרום** ל-Themed Icons של אנדרואיד 13 |
| **אייקון קטן בהתראות** | חייב להיות צללית לבנה (אחרת מוצג ריבוע אפור). צבע accent להתראה |
| פסי גלילה | מוסתרים ברשימות אופקיות. אנכיים לפי הצורך |
| "זוהר" או "מתיחה" בקצה גלילה | נשאר מתיחה של אנדרואיד 12+ (זה מקומי ונכון) |
| תווית כפתור הפעולה במקלדת | `returnKeyLabel` בעברית ("הבא", "שמירה", "חיפוש") |
| placeholder של תמונה בזמן טעינה | `expo-image` עם רקע ומעבר fade |
| בקשת הרשאות (דיאלוג מערכת) | אי אפשר לעצב, אז **מקדים לה מסך הסבר מעוצב** ("למה צריך התראות"). אם נדחתה לצמיתות, כפתור להגדרות |
| דיאלוג ההתקנה של עדכון | מערכת. מקדים לו גיליון מעוצב עם פס התקדמות ו"מה חדש" |
| תפריט הקשר של טקסט | מערכת (זה בסדר ומוכר) |

**אכיפה:**
1. **כלל lint** (`no-restricted-imports`): מחוץ ל-`mobile/src/ui/**` אסור לייבא מ-`react-native` את `TextInput`, `Switch`, `Button`, `Pressable`, `TouchableOpacity`, `TouchableHighlight`, `Modal`, `Alert`, `ToastAndroid`, `ActivityIndicator`, `RefreshControl`. ה-CI נכשל אם מישהו עוקף.
2. **גלריית עיצוב** (`app/dev/gallery.tsx`, נפתחת בשבע לחיצות על מספר הגרסה): כל רכיב בכל מצב, בכל פלטה, בבהיר ובכהה. זו נקודת האישור שלך לשפת העיצוב **לפני** שבונים מסכים.
3. **צילומי מסך אוטומטיים ב-CI** לכל מסך, בבהיר ובכהה (פרק 11). כך אני יכול לבדוק ויזואלית כל שינוי.

| טופס | היום | באנדרואיד |

## 8. התראות: הפעם זה יעבוד

### למה היום זה לא אמין

- **Web Push באנדרואיד** עובר דרך כרום ו-Service Worker. יצרנים עם ניהול סוללה אגרסיבי (Samsung, Xiaomi) מעכבים או חוסמים אותו.
- **ההתראה המקומית** רצה רק כשפותחים את האפליקציה, ורק פעם ביום.
- **הפונקציה בשרת** לא נפרסת ב-CI, דורשת Blaze, ושולחת רק לבעלים.
- **אין דרך לדעת** מה מהם לא עובד.

### התכנון החדש: שתי שכבות ואבחון

**שכבה 1: תזמון מקומי במכשיר (העיקרית, בלי תלות בשרת)**
- `shared/notifySchedule.ts` מחשב לכל תזכורת את מועדי ההתראה:
  - אותן "אבני דרך" כמו בשרת (30/14/7/3/1/0 ימים, בתוך חלון ה"מתי להתריע").
  - **בשעה שבחרת** ("שעת התראה", ברירת מחדל 09:00), או **בשעה של התזכורת** אם הוגדרה.
- `expo-notifications` מתזמן אותן ב-AlarmManager. ההתראות קופצות **גם כשהאפליקציה סגורה ובלי אינטרנט**.
- **תזמון מחדש** (ביטול הכל ותזמון חדש) בכל פתיחה, בכל שינוי בנתונים (debounce), בשינוי העדפות, **פעם ביום ברקע** (WorkManager) ואחרי הפעלה מחדש של הטלפון.
- תקרה: 60 הימים הקרובים ועד 100 התראות, בתוך המגבלה של אנדרואיד.
- הרשאות:
  - `POST_NOTIFICATIONS` (אנדרואיד 13+) עם מסך הסבר לפניה.
  - `USE_EXACT_ALARM` / `SCHEDULE_EXACT_ALARM` לדיוק בשעה. זו אפליקציה שמותקנת מחוץ לחנות, אז אין מגבלת מדיניות של Play.
  - הצעה להחריג מאופטימיזציית סוללה, עם הסבר ייעודי ל-Samsung ו-Xiaomi.

**שכבה 2: FCM נייטיב מהשרת (לשינויים ממכשיר אחר ולמשותפים)**
- הטוקן נרשם ב-`users/{uid}/fcmTokens/{token}` עם `platform: 'android'`.
- עדכון ב-`functions/index.js`:
  - payload של `android` (`channelId`, `priority: high`, `tag`).
  - **שליחה גם למשותפים**. כדי למצוא את ה-uid לפי אימייל, שומרים `users/{uid}.email` בכניסה.
  - אותה לוגיקת אבני דרך מ-`shared/`.
- **מניעת כפילויות:** השרת והמכשיר משתמשים באותו `tag` (`${reminderKey}:${milestone}`), כך שאנדרואיד **מחליף** התראה קיימת ולא מציג שתיים. (לוודא התנהגות מדויקת במימוש.)
- **פריסה ב-CI:** שלב `firebase deploy --only functions` ב-workflow. דורש Blaze; בלעדיו השלב מדלג, והשכבה המקומית עדיין עובדת.

### חוויית ההתראה

- **ערוצים:** "תזכורות" (חשיבות גבוהה, צליל ורטט), "עדכוני אפליקציה", "כללי". כל ערוץ ניתן לכיבוי בהגדרות המערכת.
- **פעולות על ההתראה:** "בוצע" (בתזכורות מותאמות), "הזכר לי מחר".
- **לחיצה על ההתראה:** מובילה ישר למסך הנכון (ביטוח, טיפולים, תזכורות) ב-deep link `car360://…`.
- **קיבוץ:** כמה התראות באותו יום מקובצות ל"3 תזכורות להיום".
- **אייקון:** צללית לבנה ייעודית וצבע accent.

### מסך אבחון ("למה לא קיבלתי התראה?")

✓/✗ לכל תנאי: הרשאת התראות · ערוץ "תזכורות" פעיל · התראות מדויקות · אופטימיזציית סוללה · טוקן FCM רשום בשרת · מספר ההתראות המתוזמנות · **ההתראה הבאה: "חידוש טסט, 12.3 בשעה 09:00"**. לצד זה:
- כפתור "התראת ניסיון מקומית"
- כפתור "התראת ניסיון מהשרת"
- לכל ✗, כפתור שמתקן אותו או פותח את ההגדרה הנכונה

## 9. עדכונים מתוך האפליקציה

### 9.1 הצינור ב-GitHub (`.github/workflows/android.yml`)

**טריגר:** push ל-`main` שנוגע ב-`mobile/**` או `shared/**`, או הפעלה ידנית.

**שלבים:**
1. checkout, Node, Java 17, `npm ci`.
2. `npx expo prebuild --platform android` (יוצר את פרויקט האנדרואיד מהקונפיגורציה, בלי EAS ובלי שירות חיצוני).
3. פענוח ה-keystore מ-GitHub Secrets.
4. `./gradlew assembleRelease`:
   - `versionCode` = מספר ההרצה של ה-workflow (עולה תמיד).
   - `versionName` = הגרסה מ-`mobile/package.json` (למשל `1.3.0`).
5. בדיקות: typecheck, lint (כולל כלל "אין ברירות מחדל"), unit tests. אם משהו נכשל, אין release.
6. **GitHub Release** עם תגית `android-v1.3.0+57`, ועליו:
   - `car360.apk` (חתום).
   - `latest.json`: `versionCode`, `versionName`, `size`, `sha256`, `notes` (הודעות ה-commit מאז הגרסה הקודמת, בעברית), `minSupportedVersionCode`.

**כתובת קבועה לבדיקה:** `https://github.com/ohavs/Car360/releases/latest/download/latest.json`.
- הריפו ציבורי, אז אין צורך בטוקן, וזו כתובת הפניה שלא נספרת במגבלת ה-API.
- **ערוץ בטא (אופציונלי):** push ל-branch שלי יוצר pre-release. מתג "ערוץ בטא" בהגדרות יבדוק גם אותם, כדי שתוכל לנסות שינוי לפני שהוא נכנס ל-`main`.

**לגבי ה-keystore:**
- כל הגרסאות **חייבות** להיחתם באותו מפתח, אחרת אנדרואיד מסרב לעדכן ("App not installed").
- אני יכול לייצר את ה-keystore ולשלוח לך אותו. אתה שומר אותו ב-Secrets, **ועוד גיבוי אחד** (מנהל סיסמאות או Drive).
- אם הוא אובד, יהיה צריך להסיר ולהתקין מחדש. הנתונים בענן, אז לא נאבד מידע.

### 9.2 הזרימה באפליקציה

```
הגדרות → "בדיקת עדכונים"
  ↓  (גם אוטומטית פעם ביום בפתיחה; תגית על לשונית ההגדרות + התראה בערוץ "עדכונים")
גיליון: "גרסה 1.3.0 זמינה" · מה חדש · 24MB · [עדכון עכשיו]
  ↓
הורדה בתוך האפליקציה עם פס התקדמות (ממשיכה אם עוברים מסך)
  ↓
אימות sha256 + גודל (הגנה מקובץ פגום או חלקי)
  ↓
התקנה דרך PackageInstaller (Expo Module ב-Kotlin, ‏modules/app-updater)
  ↓
האפליקציה נסגרת לרגע, אנדרואיד מחליף קוד, והיא עולה על הגרסה החדשה, ומציגה "מה חדש"
```

**מה אנדרואיד מרשה, בכנות:**
- **פעם אחת בחיים:** אישור "התרה להתקין מהמקור הזה" עבור Car360. האפליקציה מזהה כשזה חסר ופותחת בדיוק את מסך ההגדרה הנכון.
- **באנדרואיד 12 ומעלה:** אפליקציה שמעדכנת **את עצמה** יכולה לבקש התקנה **בלי דיאלוג אישור** (`USER_ACTION_NOT_REQUIRED` + ההרשאה `UPDATE_PACKAGES_WITHOUT_USER_ACTION`). זו החוויה של "לחיצה אחת ובלי לצאת". **לאמת על המכשיר שלך**: יש יצרנים (בעיקר Xiaomi) שמציגים דיאלוג בכל זאת. אם כן, הגיבוי הוא דיאלוג מערכת אחד של "עדכון".
- **הסגירה הקצרה אי אפשר לעקוף.** החלפת קוד נייטיב דורשת להפעיל מחדש את התהליך. אחרי ההתקנה האפליקציה נפתחת מחדש לבד כשהמערכת מאפשרת, ואחרת מופיעה התראה "Car360 עודכן, הקישו לפתיחה".

**לסדר שביקשת** ("קודם APK בגיטהאב, אחר כך הכפתור"): M1 בנוי בדיוק כך, 1א ואז 1ב. ההמלצה שלי היא ש**ה-APK הראשון שתתקין כבר יכלול את הכפתור**. ככה ההתקנה הידנית קורית פעם אחת בלבד, וכל מה שאחריה מגיע בלחיצה.

### 9.3 שדרוג עתידי אופציונלי: עדכונים בלי התקנה בכלל (OTA)

רוב השינויים הם JavaScript בלבד (מסכים, עיצוב, לוגיקה). עם `expo-updates` (דרך EAS Update, חינמי בהיקף של אפליקציה משפחתית) אפשר להוריד את הקוד החדש ולטעון מחדש **בתוך שנייה, בלי מתקין ובלי סגירה**. APK יידרש רק כשמשתנה קוד נייטיב. כפתור "בדיקת עדכונים" יבדוק את שניהם. מומלץ לשקול אחרי גרסה 1.0.
